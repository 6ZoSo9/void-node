# VOID Mainnet — Obelisk Validator Quickstart (Draft)

This document describes the *human* flow we expect for VOID mainnet validators using Obelisk Wallet.

It does **not** deploy anything and does **not** override any security plans. It just mirrors the internal
validator UX checklist in a form we can refine into public docs later.

---

## 0. Preconditions (chain must be healthy first)

Before anyone becomes a validator, the core network must already be healthy:

- `void:mainnet_overall:health:last_5m_v2 == 1`
- `void:mainnet_pillars:health:last_5m      == 1`
- `void:mainnet_lastmile:health:last_5m    == 1`
- `void_safeboot_overall_health            == 1`

Bootstrap PLAN must be handled carefully:

- `void:mainnet_bootstrap_plan:configured:last_5m == 1`
- `void:mainnet_bootstrap_plan:health:last_5m     == 0` **until** the real PLAN is filled and approved.

Normal validators should never touch PLAN. They just join an already-bootstrapped network.

## 1. Install Obelisk Wallet

Validator operators will use one of the Obelisk tiers:

- **Obelisk Lite** — browser extension (transaction signing, basic wallet).
- **Obelisk Mobile** — mobile app (future light validator / companion).
- **Obelisk Titan** — desktop or server-grade app (for heavy validators, GPU, monitoring).

Initial target for real validators is: **Obelisk Titan on a trusted machine**.

Steps:

1. Install Obelisk on a clean, trusted OS.
2. Create a new VOID account / identity.
3. Write the seed phrase on **paper**:
   - No screenshots.
   - No cloud backups.
   - No plaintext files.
4. Confirm wallet shows:
   - Network: `VOID Mainnet`
   - `chainId: 2050`
   - Your account address `0x...` (this will usually be the **reward** address).

---

## 2. Fund the reward wallet

Before registering as a validator, the reward wallet needs enough VOID for:

- Gas to submit the validator registration transaction(s).
- Gas for later maintenance/rotation operations.

The Obelisk UI must make this obvious:

- Display `Network: VOID Mainnet (2050)` clearly.
- Show the current head height from a trusted RPC (node not stuck).
- Require a basic send/receive test to succeed before enabling validator actions.

---

## 3. Validator identity and keys

A validator has two main identities:

1. **Reward address**
   - Normal EOA, controlled by Obelisk wallet.
   - Receives rewards.
   - Signs user-facing governance or operations transactions.

2. **Consensus key**
   - A dedicated keypair used by the validator node in consensus.
   - Private key must live either:
     - Inside Obelisk Titan on the validator machine, or
     - On a hardened validator server with locked-down storage.
   - Must **not** reuse the same seed as the reward wallet.

On-chain, the ValidatorSet will conceptually track:

- `reward`       → reward EOA (Obelisk wallet address).
- `consensusKey` → consensus public key bytes.
- `stakeVOID`    → amount of VOID staked/locked via RewardEngine/Treasury.

---

## 4. Run a VOID node for validator duties

Each validator must run a node (or connect to a trusted local node):

- This is a packaged mainnet build of `void-node`.
- The node is expected to expose:
  - `/head.txt`
  - `/metrics/void/head`
  - Existing exporters for:
    - txroot
    - header3
    - seals
    - proposer

These exporters are already used by internal SLOs and must remain canonical.

The Obelisk UI should support a flow like:

- “Connect to local node” (for example `http://127.0.0.1:4100`).
- Show node health derived from the same exporters used in our Prometheus stack.
- Warn loudly if the node is out of sync or unhealthy.

---

## 5. Register as a validator (conceptual flow)

Once:

- Obelisk wallet is set up.
- Reward wallet is funded.
- Node is running and healthy.

The validator registration flow should look like:

1. In Obelisk:
   - Open the “Become a validator” or “Register validator” section.
2. Provide:
   - Validator name / moniker.
   - Reward address (usually the current wallet).
   - Consensus public key (generated by Titan or imported from a secure source).
   - Intended stake amount (VOID to lock).
3. Wallet builds a sequence of transactions (exact contracts may include):
   - Locking stake in RewardEngine/Treasury.
   - Calling ValidatorSet to register the validator with `(reward, consensusKey, stake, params)`.
4. Wallet displays a final summary:
   - Contract addresses and chainId.
   - Payload details (amount staked, keys, expected effects).
   - Clear warnings about slashing/uptime expectations.
5. User explicitly confirms and signs.
6. Wallet tracks confirmations and shows final validator status.

This entire process must happen **after** mainnet bootstrap is complete and must never bypass UpdateGate/AdminGate security.

## 6. Monitoring and ongoing operations

Validator operators should have continuous visibility into:

- Validator status:
  - Active / inactive / jailed / unknown.
- Effective stake and accumulated rewards.
- Recent participation:
  - Approximate block participation or missed blocks over recent time windows.

On the backend:

- We reuse existing exporters:
  - txroot
  - header3
  - seals
  - proposer
  - head
- Obelisk and dashboards sit **on top** of those metrics.
- We do not fork truth or create competing health sources.

Later enhancements (not required for first mainnet release):

- Push/mobile notifications for:
  - Node down or high drift.
  - Validator missing blocks over a threshold window.
  - Rewards available to claim over a configured threshold.

## 7. Mobile validators (future direction)

Longer-term, we may support validator-like duties from phones using **Obelisk Mobile**:

- Phones are treated as constrained devices:
  - Limited CPU/network, battery-sensitive.
- They may pair with:
  - A Titan instance, or
  - A dedicated helper node.

Concept:

- Mobile wallet holds keys and approval power.
- Helper node performs heavy lifting:
  - Full node duties.
  - Proof generation.
  - AI-powered monitoring or automation.
- Mobile signs validator-related messages and approves operations, but does not act as a full heavy node itself.

This must be optional and explicitly opt-in.

---

## 8. Safety and keys summary

Key rules for validator operators:

- Never store seed phrases in screenshots, cloud storage, or plaintext files.
- Keep consensus keys separate from reward wallet seeds.
- Use the documented device roles:
  - LUKS-backed main device for hot-but-guarded secrets.
  - Offline paper backups for long-term recovery.
  - Hardware wallets or airgapped flows where appropriate.
- Obelisk UX must never encourage unsafe shortcuts.

This doc is a **draft** aligned with current internal design; final public docs will be generated from this and the internal checklists when mainnet is closer.
