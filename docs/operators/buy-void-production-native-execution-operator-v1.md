# Buy VOID production native-execution operator v1

Marker:

`VOID_BUY_VOID_PRODUCTION_NATIVE_EXECUTION_OPERATOR_V1`

Tracks #1135.

## Purpose

Provide the missing production operator CLI above the existing loopback-only
Buy VOID native-execution runtime without creating a second execution engine,
policy parser, nonce/fee planner, wallet path, signer path, or broadcaster path.

The existing runtime remains the sole execution authority. It reconstructs the
attempt, claim, inventory reservation, bounded execution plan, nonce/fee plan,
signer dependency, broadcaster dependency, durable submission guard, and
submission outcome from server-owned state.

This CLI only constrains how an operator may call that existing runtime.

## Runtime boundary

The operator talks only to these existing routes:

```text
GET  /__void/operator/buy-void-native-execution-v1/status
POST /__void/operator/buy-void-native-execution-v1/command
```

The destination is fixed to numeric loopback `127.0.0.1`. The only transport
configuration exposed to the operator environment is the local HTTP port:

```text
VOID_BUY_VOID_PRODUCTION_NATIVE_EXECUTION_OPERATOR_PORT
```

The default port is `4100`.

The operator rejects non-HTTP schemes, non-`127.0.0.1` hosts, userinfo, query
strings, fragments, and wrong route paths. It follows no redirects, uses a
10-second request timeout, and caps JSON responses at 1 MiB.

There is no CLI host or URL override.

## Closed CLI surface

The only business selector is:

```text
--attempt-id <64 lowercase hex>
```

Dry run is the default:

```bash
npx tsx scripts/buy_void_production_native_execution_operator_v1.ts \
  --attempt-id <attempt-id>
```

Apply mode additionally accepts only:

```text
--apply
--expected-plan-fingerprint-sha256 <64 lowercase hex>
--policy-fingerprint-sha256 <64 lowercase hex>
--confirm buyVoidNativeExecuteReservedPlan
--submission-idempotency-key <64 lowercase hex>
```

Apply-only arguments are rejected unless `--apply` is present.

The submission idempotency key is never generated by the CLI. The exact
64-lowercase-hex requirement comes from the existing durable submission guard.

The CLI has no input for:

- runtime root or data directory;
- inventory pool or execution policy;
- fulfillment wallet or signer;
- private key, mnemonic, seed, or credential;
- RPC URL or fee settings;
- destination or VOID amount;
- fulfillment intent or inventory reservation;
- bounded execution plan or transaction plan;
- raw, unsigned, signed, or prepared transaction material; or
- arbitrary HTTP endpoint.

## Status precheck

Every operation starts by reading the existing runtime status route.

The operator requires the exact native-execution runtime marker/version, exact
status/command routes, loopback-only/one-request authority, configured production
policy, valid runtime-policy and RPC fingerprints, and exact required confirmation:

```text
buyVoidNativeExecuteReservedPlan
```

It also verifies the runtime authority remains fail closed:

- disabled by default;
- dry-run allowed while disabled;
- apply forbidden while disabled;
- server-owned root/policy/RPC;
- attempt-ID-only selection;
- confirmation before apply I/O;
- injected dependencies before apply I/O;
- no raw signed-transaction input/persistence/output;
- no automatic retry;
- no receipt wait;
- no background loop; and
- no startup execution.

The raw runtime root returned by the loopback status endpoint is deliberately not
copied into the operator receipt.

## Dry-run plan

Dry run POSTs exactly:

```json
{
  "attempt_id": "<attempt-id>",
  "apply": false
}
```

No confirmation, idempotency key, policy, wallet, RPC, or transaction data is
sent by the CLI in dry-run mode.

The existing runtime may remain disabled. It still performs its already-reviewed
server-journal reconstruction and read-only nonce/fee planning. That path may read
the four allowed Chain-2050 RPC methods:

```text
eth_chainId
eth_getTransactionCount
eth_gasPrice
eth_getBalance
```

Dry run must return zero mutation, zero signing, and zero transaction broadcast.
The worker preview must also keep wallet/sign/broadcast/money authority false.

The operator does not recompute transaction economics. It validates the existing
runtime/planner/worker result and produces a sanitized execution preview containing:

- exact attempt ID;
- exact inventory-reservation ID;
- deterministic bounded-execution-plan ID;
- chain ID 2050;
- delivery address and VOID amount;
- native value;
- pending nonce;
- gas limit;
- max fee and priority fee;
- fulfillment-wallet fingerprint, not the raw wallet address;
- RPC URL fingerprint, not the raw RPC URL;
- observed gas price;
- estimated maximum transaction cost;
- observed wallet balance; and
- the exact four read-only RPC methods used.

The preview is bound with the runtime-policy fingerprint and exact execution
confirmation into a deterministic SHA-256 operator plan fingerprint.

## Apply readiness

A dry-run plan records whether the current runtime reports `apply_ready=true`.
A plan can still be reviewed while apply readiness is false.

A real apply invocation performs the entire status + dry-run plan again first.
The fresh status must prove all of these simultaneously:

```text
enabled=true
signer_configured=true
broadcaster_configured=true
apply_ready=true
```

The current runtime-policy fingerprint and newly reconstructed operator plan
fingerprint must exactly equal the operator-supplied echoes. A nonce, balance,
policy, route, dependency, journal, fee, destination, amount, or other material
change therefore invalidates the old plan rather than silently carrying it into
execution.

## Explicit value-bearing apply

Only after the fresh replan and all exact echoes pass does the CLI POST:

```json
{
  "attempt_id": "<attempt-id>",
  "apply": true,
  "confirmation": "buyVoidNativeExecuteReservedPlan",
  "submission_idempotency_key": "<64 lowercase hex>"
}
```

Those are the only four applied-command keys.

The CLI does not synthesize the confirmation or idempotency key and never retries
this request automatically.

A real applied request is value-bearing: the existing runtime may read the
credential-backed signer, sign a native VOID transfer, claim the durable
submission guard, and submit the signed transaction to the configured loopback
Chain-2050 broadcaster.

Publishing, reviewing, or merging this source does none of those things.

## Submission outcome truth

The operator preserves the existing runtime distinctions.

### `broadcast_accepted`

Accepted only when the runtime and worker both report the exact successful
attempt binding, mutation/sign/broadcast truth, matching expected/observed
transaction hash, no raw signed-transaction output, and no automatic retry.

The sanitized receipt may expose the transaction hash and bounded provider
submission ID. It does not expose a raw signed transaction.

### `not_broadcast`

A bounded `not_broadcast` result is preserved only when the runtime and worker
both report definitive non-submission and `reconciliation_required=false`.

The operator reports:

```text
submission_may_have_occurred=false
automatic_retry_allowed=false
```

No automatic retry is performed even though the underlying durable guard may
have separately classified a release reason as retry-safe.

### `broadcast_unknown`

A bounded ambiguous runtime result remains ambiguous:

```text
submission_may_have_occurred=true
reconciliation_required=true
automatic_retry_allowed=false
```

It must go to the existing reconciliation path before any later submission
decision.

### Apply transport/result ambiguity

Once the CLI has attempted the applied POST, a timeout, connection loss, malformed
response, or response that fails the expected runtime boundary cannot prove that
the server did not act.

The operator therefore emits:

```text
status=operator_transport_unknown
submission_may_have_occurred=true
reconciliation_required=true
automatic_retry_allowed=false
```

This deliberately mirrors the existing fail-closed Chain-2050 transport posture.
The CLI never converts a lost response into `not_broadcast`.

## Server-enforced plan binding

The dry-run response now carries the runtime-produced deterministic plan fingerprint. The operator requires the reviewed fingerprint and current runtime-policy fingerprint, then echoes both into the value-bearing apply request. The runtime independently recomputes its current policy fingerprint before planning and recomputes the current execution-plan fingerprint after the fresh nonce/fee/balance read but before invoking the worker. Any policy or plan drift holds before signing or broadcast.

An apply transport timeout, lost response, or malformed response is not reported as a clean no-side-effect result. Those mutation/signing/broadcast fields are indeterminate and reconciliation remains required; automatic retry remains disabled.
