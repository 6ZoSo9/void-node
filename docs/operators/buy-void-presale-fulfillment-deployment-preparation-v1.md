## Gas ceiling boundary

The prior ERC-20 delivery candidate used:

```text

```

That ceiling belongs to the previous bare `VoidToken.transfer(...)` runtime and
is intentionally **not** inherited as the payment-keyed
`fulfill(bytes32,address,uint256)` maximum gas ceiling.

The preparation records:

```text

```

until a separate review establishes an appropriate bounded ceiling.

## Ordered gates

The required sequence is:

1. review and accept this source preparation;
2. separately authorize read-only deployer/nonce/fee observation;
3. bind the selected deployer and pending nonce;
4. review the payment-keyed fulfillment gas ceiling;
5. construct the exact unsigned EIP-1559 deployment transaction without
   signing;
6. review the future CREATE address and unsigned transaction;
7. obtain separate deployment signing/broadcast authorization;
8. broadcast once and capture the receipt;
9. run the merged exact read-only deployment attestation;
10. separately attest presale inventory funding; and
11. separately authorize runtime/public activation.

## Why this comes before the final production candidate

The merged production configuration verifier requires a nonzero
`VOID_BUY_VOID_PAYMENT_KEYED_FULFILLMENT_CONTRACT_ADDRESS`.

That address cannot be truthfully fixed until a deployer + nonce define the
future CREATE address. This preparation therefore carries forward every already
reviewed production value while holding the contract address and gas ceiling
open.
